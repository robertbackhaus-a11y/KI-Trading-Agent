# Desktop-GUI

English version: [gui.en.md](gui.en.md)

Die Desktop-GUI ist ein überwiegend lesendes Cockpit für VIPER-AI. Sie zeigt, was der Trading-MCP-Server meldet, steuert die geplanten Tasks und bietet einen Chat mit einem lokalen Sprachmodell, das dieselben Daten lesen kann. Sie enthält keine Trading-Logik, keinen Datenbankzugriff und keine Orderfunktion. Geschrieben wird nur über sechs schmale, ausdrückliche MCP-Aktionen der Watchlist-Seite (Abschnitte 3 und 5); der Chat kann nur lesen. Entwicklungsstand: Die GUI hat keine eigene Versionsnummer; sie meldet `dev`.

## 1. Architektur

```
Desktop GUI (PySide6)
  |-- MCP client ----- stdio child process ----- Trading MCP server ----- SQLite
  |-- Chat ----------- Ollama HTTP API (local)   tool calls go through the MCP client
  |-- Task service --- PowerShell -------------- Windows Task Scheduler
  `-- settings file and log files
```

- Trading-Daten kommen ausschließlich aus den READ-Tools des Trading-MCP-Servers. Die ViewModels formatieren nur, was die Tools liefern, und rechnen nichts.
- Der MCP-Server läuft als eigener Kindprozess der GUI. Er wird nie importiert und kann neben einem anderen Client laufen, der seinen eigenen Serverprozess startet.
- Der Windows Task Scheduler wird direkt und nicht über MCP angesprochen, damit kein Sprachmodell einen Task starten kann.
- Der Chat spricht direkt mit dem lokalen Ollama-Server; die GUI startet oder stoppt Ollama nie.

## 2. Installation und Start

Die GUI hat eine eigene virtuelle Umgebung; die Laufzeitumgebung von VIPER-AI wird nicht verändert. `requirements-gui.txt` pinnt `PySide6-Essentials` (nicht das Metapaket `PySide6`, das auch WebEngine und die Addons nachzieht) und `mcp` (dieselbe Version wie die Laufzeit).

```
py -3.12 -m venv .venv-gui
.venv-gui\Scripts\python.exe -m pip install -r requirements-gui.txt
.venv-gui\Scripts\python.exe -m gui
```

Alternativ (pip-Installation, parallel zum Deploy): `.venv-gui\Scripts\python.exe -m pip install "<repo-path>[gui]"` installiert VIPER-AI mit dem Extra `gui` (`PySide6-Essentials`); die GUI startet dann mit `viper-ai-gui` (ohne Konsolenfenster) oder `python -m viper_ai.gui`. Ihre MCP-Einstellungen (`mcp_python_path`, `mcp_server_path`) bleiben unverändert und zeigen weiter auf den deployten Server.

Die Befehle laufen im Repository-Stammordner. Die Standardwerte zeigen auf die Installation, aus der die GUI läuft: die deployte GUI auf `<root>\.venv` und `<root>\mcp\server.py`, die pip-Installation auf ihr eigenes Python und `viper_ai\mcp\server.py`; Datenbank und Logs sind `<root>\data\trading.db` und `<root>\logs` (`<root>` = `VIPER_TRADING_ROOT`, Standard `C:\tools\trading`). Gespeicherte Einstellungen haben immer Vorrang; eine fehlende Datenbank oder ein gespeicherter MCP-Server einer anderen Installation wird als Warnung angezeigt.

## 3. Seiten

| Seite | Inhalt | Quelle |
|---|---|---|
| Dashboard | Portfolio, Allokation, Cash, External Funding, Planner-Status, geplante und zurückgestellte Entries, Blocker und Warnungen | `run_trading_orchestrator` (Detail), `database_status` |
| Planner / Actions | Engine-Aktionen je Position, geplante und zurückgestellte Entries mit Reason Codes, Sektor- und Korrelationsrisiko, `simulation_only`, `orders_created` | `run_trading_orchestrator` (Detail) |
| Watchlist | die gesamte Watchlist mit Strategie, Priorität, Rang, Score, Status, Datenqualität, News-Status und Bewertungsdatum; Filter und Sortierung; Hinzufügen, Entfernen sowie Strategie und Priorität direkt in der Tabelle bearbeiten | `get_watchlist`, `add_watchlist_candidate`, `remove_watchlist_candidate`, `set_watchlist_priority`, `onboard_security`, `set_security_strategy`, `set_security_sector` |
| Sektoren | das Portfolio nach Sektoren: Treemap (Fläche = Marktwert, Gruppierung = Sektor, Farbe = Tagesperformance), Sektor-Tabelle (Marktwert, Anteil, Anzahl Positionen, Tagesperformance, Guard-Status und Limit) und Positionstabelle; nicht zugeordnete Positionen als eigener Bereich „Nicht zugeordnet“ | `get_sector_overview` |
| Tasks | Betriebsübersicht der sieben geplanten Trading-Tasks: Rhythmus, Status mit letztem Lauf, Datenstand, letzter Erfolg, nächster Lauf, Dauer, Run now (mit Warnung bei veralteten Vorläufern), Log-Ende; unter der Tabelle der Stand der sechs ETF-Datensätze (Holdings von XUSE, IS3N, SPXS und die Sektorverteilungen; die SPXS-Sektorverteilung ist als "manuell" mit Datum und Alter markiert und macht den Task nie rot) | Windows Task Scheduler, Logdateien, `get_data_freshness` |
| Import | ein Transaktionsexport (Parqet oder kanonisches CSV): Datei wählen, „Prüfen“ (Probelauf) zeigt den Unterschied zur Datenbank und den Abgleich der Datei mit dem simulierten Endstand, offene Punkte werden direkt dort entschieden (ein Kennungs-Alias für einen ISIN-Konflikt, eine Strategie Swing / Long-Term / Keine für eine neu gehaltene Position ohne Strategie; jede Entscheidung braucht eine neue Prüfung und ergibt ein neues Plan-Token), „Importieren“ (nach einer gültigen Prüfung des aktuellen Formulars und nach einer Bestätigung) importiert in einer Transaktion und zeigt den Abgleich mit der Datenbank; die Seite startet nie eine Campaign | `check_transaction_import`, `import_transactions` |
| Chat | Fragen an ein lokales Sprachmodell, das über die READ-Tools liest; gestreamte Antwort, optionales Thinking, Tool-Status, Stop, Neuer Chat | Ollama, MCP-Tools |
| Diagnostics / Settings | MCP-, Datenbank- und Ollama-Status, Pfade, Tool-Klassifizierung, Schema-Hash, letzter Chat-Fehler, Einstellungsformular, MCP-Neustart | `database_status`, Einstellungsdatei |

Die Watchlist-Seite ändert die Watchlist nur über schmale, ausdrückliche Aktionen: Hinzufügen (ein Wertpapier, das bereits im Security Master steht; die optionale Prüfung löst es nur auf), Entfernen (nach einer Bestätigung, deren Standard Abbrechen ist; eine gehaltene Position bleibt unberührt) sowie die Bearbeitung von Strategie und Priorität direkt in der Tabelle (unten; es gibt dafür keinen zweiten, sofort schreibenden Dialog). Ein Wertpapier, das nicht im Security Master steht, wird beim Hinzufügen nie angelegt; der Dialog sagt das und bietet dann die Schaltfläche „Neues Wertpapier aufnehmen“ an. Die Aktions-Tools stehen im Chat nicht zur Verfügung.

**Strategie und Priorität direkt in der Tabelle.** Genau zwei Spalten sind bearbeitbar: Strategie (Auswahl: Keine, Swing, Long-Term – nur die Werte, die es gibt) und Priorität (ganze Zahl, leer = keine; die bestehende Semantik). Ein Doppelklick öffnet den Editor; eine Auswahl schreibt **nichts**, sondern markiert die Zeile als „Geändert“ (fett, Markierung in der Spalte „Änderung“). Erst „Änderung übernehmen“ speichert die markierte Zeile: zuerst die Strategie über `set_security_strategy`, nur bei Erfolg danach die Priorität über `set_watchlist_priority`; bei einem Fehler wird nicht blind weitergeschrieben, der nicht gespeicherte Teil bleibt markiert, und die Liste wird neu geladen (das Backend ist die Wahrheit). „Änderung verwerfen“ setzt die Zeile zurück. Ein Neuladen mit ungespeicherten Änderungen fragt „Ungespeicherte Änderungen verwerfen?“ (Standard: Abbrechen); Filter, Sortierung und Seitenwechsel behalten sie. **Gehaltene Positionen** haben keinen Strategie-Editor und eine **aktive Campaign** blockiert die Änderung (lesbare Meldung; der Original-Code steht im Tooltip), denn die Strategie hängt dort am Campaign-Ablauf. Eine Strategie setzt nur die Zuordnung: Es wird keine Campaign angelegt und keine Order erzeugt; ein nicht gehaltenes Wertpapier mit Swing behandelt der Planner danach als Einstiegskandidat (nur Simulation). Das Tool steht im Chat nicht zur Verfügung.

**Seite Sektoren.** Rein lesend (`get_sector_overview`, keine Schreibaktion, keine Änderung am Risk Guard). Die offenen Positionen werden nach dem wirksamen Sektor gruppiert – derselbe Sector-Map-Zugriff wie bei Risk Guard und News-Mapping (lokaler Eintrag vor öffentlichem Eintrag). Der Marktwert ist der EUR-Wert des Portfolio-Kontexts (Stückzahl × EUR-Kurs), der Anteil bezieht sich auf den investierten Wert (die Summe der bewerteten Positionen, also die Basis des Sector Guards); Cash zählt nicht mit. Die Treemap zeigt je Sektor eine Fläche mit seinen Positionen: Fläche = Marktwert, Farbe = Tagesperformance (grün/rot, ab ±3 % volle Farbe, grau = keine Daten – eine fehlende Tagesperformance wird nie als 0 % dargestellt). Die Tagesperformance einer Position ist `close / previous_close - 1` der beiden letzten Tagesbalken (Handelswährung, ohne Währungseffekt; ein fehlender oder veralteter Balken heißt „keine Daten“); die eines Sektors ist die wertgewichtete Änderung seiner Positionen mit Daten (bei Teildeckung steht der gedeckte Anteil dabei). Positionen ohne Sektor-Eintrag bilden den eigenen Bereich „Nicht zugeordnet“ (gestrichelt); sie werden nie verworfen und nie einem anderen Sektor zugeschlagen. Die Spalte „Guard / Limit“ zeigt das Limit des Sector Guards (30 % des investierten Werts) und ob der Sektor darunter liegt, darüber („Über Limit“) oder nicht bewertet ist (nicht zugeordnet); der Guard blockiert nur Zukäufe, die den Sektor über das Limit heben würden. **ETF-Look-through.** Ein ETF mit offizieller Anbieter-Sektorverteilung wird in seine Kategorien aufgeteilt (Marktwert × Gewicht; die Gewichte werden auf 100 % normiert, damit gerundete Anbieterwerte keinen Wert erzeugen). Eine Kategorie, die auf genau eine Sektor-Gruppe passt (Financials, Health Care, Energy, Utilities, Materials, Consumer Staples), erhöht diese Gruppe als Beitrag „ETF-Look-through“. Eine Kategorie, die zu keiner einzelnen Gruppe passt (zum Beispiel Information Technology, das Halbleiter, Software und Hardware umfasst; ebenso Industrials, Communication, Consumer Discretionary, Real Estate, Cash/Derivate, „Other“), bleibt eine eigene Gruppe „… (ETF, nicht zuordenbar)“ – sie wird nie nach Namen oder Größe in eine Gruppe gelegt. Ein ETF ohne verwendbare Verteilung (keine Daten, ungültige oder unvollständige Gewichte, keine ISIN) bleibt eine unaufgelöste Position und ist in der ETF-Tabelle mit seinem Status sichtbar; eine veraltete Verteilung (älter als 120 Tage) wird genutzt und markiert. Die Tabelle zeigt je Sektor die effektive Exposure (direkt + ETF-Look-through), den direkten Anteil, den Look-through-Anteil, die Zahl der direkten Positionen und ETF-Beiträge sowie Guard-Limit und Status; die Kopfzeile zeigt die Look-through-Abdeckung (Anteil des ETF-Werts mit Daten und Anteil davon in Sektor-Gruppen). In Treemap, Tooltip und Positionstabelle steht bei jedem Eintrag, ob er direkt oder aus dem ETF-Look-through stammt (gestrichelter Rand). Die Verteilungen liegen in `etf_lookthrough_local.json` (privat, nicht versioniert, je ETF-ISIN mit Anbieter, Stand und Quelle), die Zuordnung der Anbieter-Kategorien in `etf_sector_mapping_v1.json` (versioniert); `sector_map_local.json` wird nicht verwendet oder verändert. **Der Risk Guard wertet weiterhin nur die direkte Zuordnung aus**; Limit und Status der Seite beziehen sich auf die effektive Exposure und blockieren nichts. Eine direkte Zuordnung ändert man weiterhin auf der Watchlist-Seite. Eine Firma in einem ETF zählt in dem Projekt-Sektor, den ihr eigenes Wertpapier hat (Herkunft „ETF-Einzelfirmen“, `etf_company`; dasselbe Matching wie bei der effektiven Exposure: ISIN, geprüfter Alias, Ticker und Börse, nie unscharf) und wird aus ihrer Anbieter-Kategorie herausgerechnet; Firmen ohne Sektor bleiben in ihrer Anbieter-Kategorie („nicht bewertet“), die Summe bleibt gleich. Der Risk Guard ist unverändert.

**Tab „Einzelwertrisiko“ (Effective Exposure).** Eine zweite Registerkarte der Seite Sektoren zeigt das Klumpenrisiko auf Firmenebene (`get_effective_exposure`, rein lesend): direkte Position + Anteil derselben Firma in allen gehaltenen ETFs = effektive Einzelwert-Exposure, mit Direkt-, ETF- und Effektiv-Wert und -Anteil getrennt, den beitragenden ETFs und der Liste der größten Firmen (Top 25). Der Anteil eines ETF ist sein Marktwert × das Gewicht der Holding laut Anbieter-Datei (iShares: vollständige Holdings-Datei, Gewichte als Anteil am Fondsvermögen; Cash, Futures und FX sowie der nicht erklärte Rest stehen unter „Sonstiges“ und werden nie auf Firmen verteilt). Bei einem synthetischen ETF zählt die Index-Zusammensetzung (Invesco: Benchmark-Komposition des Swaps, nicht der Collateral-Korb); seine veröffentlichten Gewichte werden unverändert verwendet und nicht auf 100 % skaliert (die Liste ist grob gerundet und summiert sich auf mehr als 100 %; eine Skalierung würde diesen Fehler in die großen Namen schieben, auf die es ankommt); der Überschuss steht als negative „Rundungsabweichung“. Die Zuordnung einer Holding zu einem Wertpapier des Portfolios läuft nur exakt: über die ISIN, über eine geprüfte Zuordnung der Holdings-Datei (zum Beispiel ADR und Stammaktie desselben Emittenten) oder über denselben Ticker an derselben Börse; sonst bleibt die Holding eine eigene Firma, mehrdeutige Fälle sind sichtbar. Gattungen eines Emittenten (Alphabet A und C) zählen über eine geprüfte Gruppe als eine Firma. Eine Firma wird nur einmal aggregiert, auch wenn sie direkt und in mehreren ETFs vorkommt. Jeder Euro des Werts steht in genau einer Gruppe: „direkt gehalten“ (Firmen mit Direktposition samt ihrem ETF-Anteil), „nur über ETFs“ (eindeutig identifizierte Firmen ohne Direktposition – dass sie nicht im Security Master stehen, ist kein Mangel), „unklar / nicht zuordenbar“ (mehrdeutige Zuordnung, Holdings ohne ISIN und Ticker, ETFs ohne Holdings), „Sonstiges“ (Cash, Derivate, nicht erklärter Rest eines physischen ETF) und die „Rundungsabweichung“. Die Holdings liegen in `etf_holdings_local.json` (privat, nicht versioniert, mit Anbieter, Stand und Quelle je ETF). Ganz oben zeigt der Tab die größte effektive Einzelposition mit ihrem Direkt- und ETF-Anteil, die Zahl der Firmen über 5 % und über 10 % (nur Anzeige, kein Limit) und ob die Holdings-Daten aktuell, veraltet oder unvollständig sind. Die Firmentabelle ist standardmäßig nach Effektiv % absteigend sortiert (jede Spalte lässt sich sortieren, „—“ steht am Ende), die Effektiv-Spalten sind hervorgehoben, Direkt und ETF bleiben getrennt, und wo es keine Direktposition oder keinen ETF-Anteil gibt, steht „—“ statt 0. Die Spalte „Datenstand“ nennt je beitragendem ETF den Stand der Holdings (veraltete sind markiert), der Tooltip zusätzlich Quelle und Zuordnung. Über der Tabelle zeigt eine eigene Treemap eine Kachel je Unternehmen (Fläche = effektiver Wert aus direkter Position und ETF-Anteilen zusammen, Farbe = Tagesperformance der Aktie; ohne eigene Aktie, etwa bei Firmen nur über ETFs, bleibt sie grau – die Performance eines ETF wird nie als Unternehmensperformance verwendet), dazu getrennte Blöcke „Weitere Firmen“ und „Sonstiges“. Sie nutzt `get_effective_exposure` (höchstens 40 Firmen) und ist unabhängig von der Sektor-Treemap, die im Tab „Sektoren“ bleibt. Der Tooltip einer Kachel nennt Effektiv-, Direkt- und ETF-Wert und -Anteil, die beitragenden ETFs mit Datenstand und Quelle sowie Zuordnungshinweise (geprüfte Zuordnung, Emittenten-Gruppe). Die Rundungsabweichung erscheint nie als Firma oder Kachel. Die Karte zeigt je ETF Abdeckung, Verknüpfung und fehlende Daten. Es wird kein Limit angewendet; **der Risk Guard ist unverändert**.

**Sektor in der Tabelle.** Die Spalte „Sektor“ zeigt die Sektor-Gruppe aus der Sector-Map (die der Risk Guard und das News-Mapping verwenden, nicht eine Datenbankspalte). Ein Zusatz „(lokal)“ und der Tooltip zeigen die Herkunft: aus `sector_map_v1.json` (öffentlich), aus `sector_map_local.json` (lokaler Eintrag, der einen öffentlichen Wert ersetzen kann – der ersetzte Wert steht im Tooltip) oder „nicht zugeordnet“ (der Sector-Guard bewertet das Wertpapier dann nicht). Die Auswahl bietet nur vorhandene Gruppen; bei einem lokalen Eintrag zusätzlich „Lokale Zuordnung entfernen“ (es gilt wieder der öffentliche Wert, falls vorhanden). Es läuft derselbe Ablauf wie bei Strategie und Priorität: Auswahl, Markierung als „Geändert“, erst „Änderung übernehmen“ speichert (nach Strategie und Priorität) über `set_security_sector`. Geschrieben wird ausschließlich `sector_map_local.json` (die vorherige Fassung bleibt als `.bak`); `sector_map_v1.json` und die Datenbank bleiben unberührt. Gehaltene Positionen und offene Campaigns blockieren die Sektor-Änderung nicht, denn sie ist eine Klassifikation, kein Lifecycle-Wechsel. Das Tool steht im Chat nicht zur Verfügung.

**Neues Wertpapier aufnehmen.** Der eigene Dialog legt genau ein Wertpapier an, ausschließlich aus den Angaben, die dort stehen: Symbol, Name und Art (Aktie oder ETF) sind Pflicht; ISIN, WKN, Börse, Währung, Land sowie ein Yahoo- und ein FMP-Symbol sind optional. Es wird nichts recherchiert, ergänzt oder geraten (keine ISIN, keine Börsenendung, kein Yahoo-Symbol, kein Sector, keine CIK). „Prüfen“ ist ein Trockenlauf: Er normalisiert die Eingaben, prüft ISIN (mit Prüfziffer), Symbol, WKN und Provider-Symbole gegen den Security Master und zeigt entweder „Keine Konflikte gefunden.“ mit einer Zusammenfassung oder alle Konflikte in Klartext; die technischen Codes stehen nur im Tooltip. „Anlegen“ ist erst nach einer Prüfung ohne Konflikte aktiv und wird bei jeder Änderung der Eingaben wieder gesperrt. Das Anlegen läuft in einer einzigen Transaktion (Wertpapier, Provider-Symbole und auf Wunsch der Watchlist-Eintrag) und wird bei jedem Fehler vollständig zurückgenommen. Existiert das Wertpapier schon, wird kein zweites angelegt und das vorhandene nicht verändert; der Dialog zeigt Symbol, Name und `security_id` und bietet an, es über die gewöhnliche Aktion zur Watchlist hinzuzufügen. Der Sector bleibt „nicht zugeordnet“. Es werden keine Strategie, Kampagne, Position oder Order angelegt und keine Marktdaten, Fundamentaldaten oder News geholt; Marktdaten werden beim nächsten regulären Lauf ergänzt. Das Tool `onboard_security` steht im Chat nicht zur Verfügung.

Technische Reason Codes (z. B. `STOPPED_SWING_MAX_REACHED`) werden als kurzer deutscher Text angezeigt; der Tooltip enthält die Erklärung und den Originalcode. Die Backend-Codes bleiben unverändert, und ein unbekannter Code wird lesbar aufbereitet angezeigt.

## 4. MCP-Client

- Das offizielle `mcp`-SDK startet den Server als stdio-Kindprozess. Die Client-Session gehört einem eigenen QThread mit eigenem asyncio-Loop.
- Alle Pfade sind absolut, insbesondere `TRADING_DB_PATH`; ein relativer Datenbankpfad bricht die lesenden Tools des Servers.
- Jeder Aufruf hat ein Timeout. Etwa alle fünf Sekunden läuft eine billige Lebendprüfung; stirbt der Kindprozess, zeigt der Status einen Fehler und der nächste Aufruf verbindet neu. Restart MCP startet nur den Kindprozess neu und verändert keine Trading-Daten.
- Die stderr-Ausgabe des Servers geht in eine eigene Logdatei.
- Nichts hängt von `capabilities.experimental` ab.

## 5. Lese- und Aktions-Tools

| Klasse | Tools | GUI |
|---|---|---|
| READ | die 17 Lese-Tools, zum Beispiel `database_status`, `run_trading_orchestrator`, `get_watchlist`, `get_sector_overview`, `get_data_freshness`, `get_effective_exposure` | erlaubt; die Seiten rufen nur `database_status`, `run_trading_orchestrator`, `get_watchlist`, `get_sector_overview`, `get_data_freshness` und `get_effective_exposure` auf, der Chat bietet dem Modell alle 17 an |
| ACTION | `approve_swing_promotion`, `sql_execute` | verweigert, dem Modell nie angeboten und vom Server der GUI gar nicht registriert (Profil `gui`) |
| ACTION (Watchlist) | `add_watchlist_candidate`, `remove_watchlist_candidate`, `set_watchlist_priority` | nur über die ausdrücklichen Schaltflächen der Watchlist-Seite (`call_action`); dem Modell nie angeboten, von `call` verweigert |
| ACTION (Strategie) | `set_security_strategy` | nur über „Änderung übernehmen“ der Watchlist-Seite (`call_action`); dem Modell nie angeboten, von `call` verweigert |
| ACTION (Sektor) | `set_security_sector` | nur über „Änderung übernehmen“ der Watchlist-Seite (`call_action`); schreibt nur die lokale Sector-Map; dem Modell nie angeboten, von `call` verweigert |
| ACTION (Security Master) | `onboard_security` | nur über den Dialog „Neues Wertpapier aufnehmen“ der Watchlist-Seite (`call_action`, erst Trockenlauf, dann Anlegen); dem Modell nie angeboten, von `call` verweigert |
| ACTION (Import) | `check_transaction_import`, `import_transactions` | nur über die Schaltflächen „Prüfen“ und „Importieren“ der Seite Import (`call_action`; der Import mit dem Token der Prüfung und nach einer Bestätigung); nie dem Modell angeboten, von `call` abgelehnt |

Die Tabelle liegt in `gui/services/tool_policy.py`; ein Test verlangt, dass jedes Tool des Servers klassifiziert ist. Aktionen sind in der Oberfläche sichtbar von Lesezugriffen getrennt und stecken nie hinter einem Lesezugriff.

## 6. Chat

- Der Ollama-Client nutzt nur die Standardbibliothek. Er streamt `/api/chat` (Antworttext, Thinking-Text, Tool Calls), und Stop schließt die HTTP-Verbindung genau dieser einen Anfrage. Die GUI startet, stoppt, lädt oder entlädt weder Ollama noch ein Modell und setzt keine Kontextgröße, sodass sie dieselbe Ollama-Instanz mit anderen Clients teilen kann.
- Modell und Thinking-Schalter kommen aus den Einstellungen `ollama_model` und `think_enabled`; das Modell wird nur dort gewechselt. Das Öffnen der Seite fragt Ollama nur nach Version und Modellnamen; geladen wird das Modell erst durch die erste Frage.
- Der Tool-Loop ist eine kleine eigene Umsetzung ohne jedes Framework: Frage, `/api/chat`, Tool Calls, Prüfung, MCP-Aufruf, Ergebnis als Tool-Nachricht, wieder `/api/chat`, bis zur Antwort. Höchstens 6 Tool-Runden je Frage; danach endet die Anfrage mit einem Hinweis.
- Angeboten werden nur die READ-Tools der MCP-Discovery, mit Name, Beschreibung und Schema unverändert. Ein Aufruf von allem anderen wird mit `TOOL_NOT_ALLOWED` beantwortet und erreicht den MCP-Server nie. Argumente werden vorher validiert (`TOOL_ARGS_INVALID`). Die Parameter `detail` und `table` werden aus den angebotenen Schemas entfernt und auf false erzwungen (nur bei Tools, die sie haben), damit die kompakten Ansichten in den Kontext passen. Ein Ergebnis über 40.000 Zeichen (`TOOL_RESULT_TOO_LARGE`) oder jenseits von 80.000 Zeichen je Frage (`TOOL_RESULT_BUDGET`) wird dem Modell nicht übergeben.
- Der Verlauf zeigt Nutzer, Assistent, Thinking, Tool-Aufruf, Tool-Status und Fehler getrennt. Tool-Ergebnisse werden nie vollständig gezeigt: nur Tool-Name, Dauer und Größe.
- Es läuft nur eine Anfrage gleichzeitig. Der Verlauf bleibt im Arbeitsspeicher, Neuer Chat setzt ihn zurück, und nichts wird auf die Platte geschrieben; in Folgefragen werden ältere Tool-Ergebnisse durch einen einzeiligen Platzhalter ersetzt. Der Systemprompt ist kurz und steht im Code (`SYSTEM_PROMPT`).

## 7. Task-Steuerung

- Nur die sieben Trading-Tasks werden abgefragt und gestartet: `Trading-MarketData-Backfill`, `Trading-FXRates-Backfill`, `Trading-EventsNews-Backfill`, `Trading-Fundamentals-SEC`, `Trading-Candidate-Discovery`, `Trading-Market-Intelligence` und `Trading-ETF-Refresh`.
- Der Status wird mit PowerShell als JSON gelesen, nie als lokalisierter Text.
- Run now fragt nach einer Bestätigung und startet dann den bestehenden Task mit `Start-ScheduledTask`. Es startet nie das Skript hinter dem Task und ändert nie eine Task-Definition. Ein laufender oder deaktivierter Task kann nicht gestartet werden; die Scheduler-Einstellung `IgnoreNew` bleibt in Kraft.
- Ein gestarteter Task darf wie geplant das Netz nutzen und in die Datenbank schreiben; deshalb ist Run now als Aktion gekennzeichnet.
- **Unsichtbare Ausführung.** Die geplanten Tasks starten `pythonw.exe` (ohne Konsole) mit dem Starter `Run-TradingTask.py <log> <script> [args]`; es öffnet sich kein cmd-, PowerShell- oder Python-Fenster, und einem Spiel wird kein Fokus genommen. Der Starter hängt stdout und stderr wie bisher an dasselbe Log an und gibt den Exitcode des Skripts an den Scheduler weiter, Ergebnisse und Logs bedeuten also dasselbe wie vorher. Die Details eines Tasks nennen „Ausführung: unsichtbar“ oder, bei einem Task, der noch `cmd.exe` startet, wie man ihn umstellt (`Manage-TradingTasks.ps1 -Action UpdateAction`, einmalig nach dem Deploy; ersetzt nur die Aktion).
- **Jetzt ausführen.** Eine Aktion je Task: Nach der Bestätigung wird der vorhandene geplante Task gestartet, es ist also derselbe Job mit derselben Aktion, denselben Einstellungen und demselben Log wie nach Plan; die Seite ruft PowerShell ohne Fenster auf. Die Zeile über der Tabelle begleitet den Lauf (Start, läuft seit, beendet mit Exitcode, z. B. „Ergebnis OK (Exitcode 0)“ oder „Fehler (Exitcode 3)“, die letzte Fehlerzeile des Logs), und die Log-Ansicht lädt das Log-Ende, wenn der Lauf endet. Ein laufender, deaktivierter oder gerade gestarteter Task wird nicht noch einmal gestartet.
- Die Log-Ansicht lädt nur das Ende der Logdatei aus dem Log-Ordner und verändert die Datei nie.
- **Betriebsübersicht.** Je Task zeigt die Tabelle den Rhythmus (aus den Auslösern: täglich, wöchentlich, 2× täglich, bei Anmeldung), den Status mit letztem Lauf und Ergebnis, den Datenstand der erzeugten Daten, den letzten Erfolg, den nächsten Lauf und die Dauer; der Tooltip nennt zusätzlich die Auslöser, `StartWhenAvailable`, `IgnoreNew`, das Zeitlimit, verpasste Läufe, die Abhängigkeiten, den letzten Fehler und den Log-Pfad. Die Task-Definitionen werden nur gelesen, nie geändert.
- **Datenstand statt Exit-Code.** Ein Task kann mit Exit-Code 0 enden und trotzdem nichts Neues geholt haben (zum Beispiel SEC-Events mit HTTP 403). Der Datenstand kommt deshalb aus den Daten selbst über `get_data_freshness`: letzter Kurs je gehaltener Position, FX-Datum je Währung, letzter Abruf von News, Fundamentals-Stand und `generated_at` der beiden Reports (sie werden nur nach einem vollständigen Lauf geschrieben). Bewertet wird mit den vorhandenen Regeln des Projekts (`market_data_max_age_days`, `fx_max_age_days`, `report_max_age_hours`), sonst aus dem Rhythmus: „aktuell“ bis zum nächsten regulären Lauf plus Karenz, „veraltet“ nach mehr als einem verpassten Lauf. Ein erfolgreich gelaufener Task mit veralteten Daten ist farbig markiert. Die Ausnahme ist Fundamentals: Der wöchentliche Task schreibt nur neue Filings, deshalb wird er am letzten erfolgreichen Lauf und am Rhythmus gemessen (aktuell bis 8 Tage, veraltet nach 15 Tagen oder bei einem fehlgeschlagenen oder verpassten Lauf); das jüngste Filing und die jüngste Periode werden nur zur Information gezeigt. Der letzte Erfolg ist der Zeitpunkt, zu dem die Daten den Erfolg belegen, oder der letzte Lauf mit Exit-Code 0; er kann vom letzten Lauf abweichen. Die Dauer ist ungefähr (Start bis letztes Schreiben des Logs), weil der Scheduler keine Laufzeit speichert; „Log-Hinweis“ zeigt die letzte fehlerverdächtige Zeile am Ende des Logs.
- **Abhängigkeiten sind fachlich, keine Task-Kette.** Sie stammen aus dem Code der Skripte: `Trading-Candidate-Discovery` liest die FX-Kurse der Datenbank (EUR-Umrechnung; sonst `UNSUPPORTED_CURRENCY`), holt die Kurse aber selbst von Yahoo und braucht weder Marktdaten noch News. `Trading-Market-Intelligence` liest die gespeicherten News und SEC-Events (Events/News) und optional den letzten Discovery-Report (ohne Report läuft sie weiter), aber keine Kurse und kein FX. Marktdaten, FX, Events/News und Fundamentals brauchen keinen anderen Task; Fundamentals läuft wöchentlich und eigenständig. Ist vor einem manuellen Start ein nötiger Vorläufer veraltet oder fehlgeschlagen, steht das lesbar in der Bestätigung; es wird nie automatisch ein anderer Task gestartet.

## 8. Einstellungen und Logging

- Die Einstellungsdatei ist `%LOCALAPPDATA%\TradingAgentGui\settings.json`. Eine fehlende Datei bedeutet Standardwerte; eine kaputte Datei oder ein ungültiger Wert fällt mit einer Warnung auf den Standardwert zurück. Es gibt keine Secrets.
- Einstellungen: `ollama_base_url`, `ollama_model`, `mcp_python_path`, `mcp_server_path`, `trading_db_path`, `trading_logs_dir`, `default_detail_mode`, `think_enabled`, `refresh_interval_s` und `window_geometry`.
- Das GUI-Log ist `%LOCALAPPDATA%\TradingAgentGui\gui.log` (rotierend). Es hält Start und Stopp, MCP-Verbindung und -Trennung, Tool-Name, Dauer und Ergebnisgröße, Ollama-Anfragen (Modell, Dauer, Tool-Runden, Abbruch, Fehler) und Task-Starts fest. Fragen, Antworten, Tool-Ergebnisse und Portfolio-Werte schreibt es nie.
- Die stderr-Ausgabe des MCP-Servers wird nach `%LOCALAPPDATA%\TradingAgentGui\mcp-stderr.log` geschrieben.

## 9. Threading

- Der GUI-Thread blockiert nie. MCP-Aufrufe laufen im asyncio-Thread; das Ergebnis kommt über ein gequeutes Signal an einen Callback im GUI-Thread.
- PowerShell, Log-Lesen und die Ollama-Prüfung laufen in einem Thread-Pool (`QThreadPool`).
- Der Ollama-Stream und der Tool-Loop laufen in einem eigenen Worker-Thread; ein Tool-Aufruf wird an den MCP-Thread übergeben und der Worker wartet darauf, sodass die Client-Session nur von ihrem eigenen Thread benutzt wird.
- Es gibt kein `qasync` und kein `QtAsyncio`.

## 10. Tests

```
.venv-gui\Scripts\python.exe -m unittest discover -s tests/gui -p "test_*.py"
```

- Die Qt-Tests laufen offscreen (`QT_QPA_PLATFORM=offscreen`). Ohne PySide6 werden sie übersprungen; die Tests von Policy, Einstellungen, ViewModels, Task-Service, Ollama-Client und Tool-Loop laufen in jeder Umgebung.
- Der MCP-Client wird gegen einen kleinen Fake-stdio-Server getestet, der dasselbe SDK nutzt: Start, Discovery, Aufruf, Timeout, Neustart, Absturz und Shutdown.
- Der Ollama-Client und der Chat werden gegen einen geskripteten Fake-Ollama-HTTP-Server getestet: Streaming, Thinking, Tool Calls, Runden, Limits, Fehler, Stop und die Folgeanfrage, nur mit synthetischen Daten.
- Die ViewModels werden mit Ergebnissen des echten Orchestrators und Planners auf synthetischen Daten getestet.

## 11. Bekannte Grenzen

- Nur lesend: In dieser Version gibt es keinen Import, keine Campaigns-Seite, keine Orderfunktion und keine Strategieänderung; der Chat kann kein Aktions-Tool aufrufen.
- Der Chat sieht nur die kompakten Ansichten; Drilldown-Ergebnisse (`detail`) sind für das Modell nicht verfügbar.
- Das detaillierte Orchestrator-Ergebnis ist nicht wie die kompakte Ansicht versioniert; die ViewModels lesen es defensiv und zeigen für Fehlendes einen Strich.
- Run now braucht PowerShell; ohne sie zeigt die Seite den Fehler und nichts wird gestartet.
- Die Aktualisierung ist manuell plus ein moderates Intervall; die Statusleiste zeigt den letzten erfolgreichen Refresh.

## 12. Deployment

Die GUI wird mit demselben Skript deployt wie die Laufzeit. Das Manifest hat die Gruppen `gui`, `gui-services`, `gui-viewmodels`, `gui-views` und `gui-requirements`; sie kopieren das Paket nach `gui\` im Produktionsstamm und `requirements-gui.txt` in den Produktionsstamm. Tests, Dokumentation und die Umgebung werden nie kopiert. Die Umgebung `.venv-gui` wird im Produktionsstamm aus `requirements-gui.txt` erzeugt (der Deploy legt sie nicht an); die Laufzeitumgebung bleibt unangetastet.

```
C:\tools\trading\.venv-gui\Scripts\python.exe -m gui
C:\tools\trading\.venv-gui\Scripts\pythonw.exe -m gui
```

Der erste Befehl startet die GUI mit Konsole, damit Fehler sichtbar bleiben, der zweite ohne Konsolenfenster. Es gibt keine Desktop-Verknüpfung, keinen Installer und keinen Autostart.

## 13. Desktop-Start

Die Desktop-Verknüpfung KI TA startet die GUI direkt, ohne Batch-Datei und ohne Skript dazwischen. Der Chat ist produktiv verfügbar und nur lesend.

- Ziel: `C:\tools\trading\.venv-gui\Scripts\pythonw.exe` mit dem Argument `-m gui`, sodass kein Konsolenfenster erscheint.
- Arbeitsverzeichnis: `C:\tools\trading`.
- Icon: `C:\tools\ki\ki-ta-icon.ico`, neben dem Icon der vorhandenen KI-Start- und Stopp-Verknüpfungen. Es folgt deren Look (türkiser Kreis, weiße fette Schrift) und zeigt KI und TA in zwei Zeilen, sodass es sich klar unterscheidet. Es ist ein Multi-Resolution-Icon (16 bis 256 Pixel, 32 Bit mit Transparenz).
- Die GUI startet oder stoppt Ollama nie; sie spricht nur mit einer laufenden Instanz, also Ollama wie gewohnt vorher starten.
- Der Chat speichert keinen Verlauf auf der Platte, und Stop bricht nur die aktuelle Anfrage ab.
